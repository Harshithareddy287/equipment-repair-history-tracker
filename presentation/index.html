Every row is checked at the door

Visit sheets and stock counts arrive as files. Before anything is saved, every row is checked: is there a machine, a real date, a sensible quantity, a known outcome, a valid part number?

Type a row and see what the loader does with it

Serial and part numbers are trimmed and uppercased first. The part-number format comes from the manager's settings file, so a new format is a settings change, not a code change.

Try: change PATTERN to r"^P-\d{4,5}$" and the row is accepted. Or try a date of 2026-02-30, a quantity of 0, or an outcome of maybe.
This is the answer to "what if part numbers change format?" Run it once (rejected), change the pattern, run again (accepted). Point out " sw-7777 " became "SW-7777".

  • A visit that used two parts is one row in visits and two in parts_used.
  • Stock can go below zero. A negative count is how a shortfall stays visible.
  • parts_used doesn't point at stock, so a part missing from the stock list can still be saved and flagged later. That's what makes the 1.1.0 rollback safe.
  • Ten years at 20 visits a day is 73,000 visits in a 9.8 MB file.
Arrows are foreign keys, which SQLite only enforces because connect() turns them on for every connection. The pink dashed line is the link we chose not to add.

Every visit is saved whole, or not at all

Each visit is one transaction: the machine, the visit, its parts and the stock change. One visit in the database is one paper visit sheet, so any record can be checked by hand.

The stock count followsThe sample batch saves 40 visits and 46 parts. P-1180 had 1 on hand and a visit used 3, so the database says -2, and keeps saying it.
A failed save leaves nothingA visit whose second part breaks a schema rule is rolled back: 0 visits, 0 parts saved, and P-1001 stays at 10 on hand.
Duplicates change nothingLoading the same visit again saves 0 and reports 1 duplicate. Re-running yesterday's file never counts a part twice.
All three results come from running save_visits on test data. Without the transaction, P-1001 would drop to 8 with no visit to explain it.

The rules read the whole history, not just today's file

One run over the sample history catches all three problems: a switch that keeps failing, parts at or under their reorder level, and a part used past zero.

The repeat-failure limits come from the manager's settings, so changing them is an edit to a file.

Try: COUNT = 2 or WINDOW = 120 and run again. More serials light up, with no code change.
Run with the defaults and read the three counts: 1 repeat failure (SW-4410), 3 low stock, 1 shortfall (P-1180, which is also low stock because -2 is under its reorder level). In the timeline only SW-4410 is shaded. SW-5120 has the most visits but they are months apart, which is what the rule is for. Then set COUNT = 2 live.

Tested on every change, drilled before every release

Covered on every pull request

  • Each loader rejection reason and each settings error
  • Rollback of a half-saved visit, and reruns that save nothing twice
  • Each rule alone, a serial breaking two rules, a day with no flags
  • An integration test: the real command line end to end, checking the report and row counts
  • The Docker image builds

Checked before every release

  • A backup is taken and its copy passes an integrity check
  • Upgrade to 1.1.0, then roll back to 1.0.0, on one volume
  • The history survives removing the container

We run this drill from a clean volume, and ran it twice for 1.1.0.

Left: what runs automatically on every pull request. Right: the release drill, shown on the Upgrade and rollback slide and in the live demo. If asked how the upgrade could be automated, the answer is a CI job that runs both image tags on one named volume.
