1.0.0, then 1.1.0
The customer is a company that repairs servers and network gear. Every visit, a technician records the machine and the parts used. Our tool keeps that history and flags two kinds of problems. It only flags them: it doesn't order parts or schedule repairs. Walk the four stations left to right; each one is one of us.

Fake data, real problems planted on purpose

Every serial, part and technician is made up. The generator plants one example of each problem, so every rule has something to catch.

The same seed always writes the same files, so the demo never surprises us.

A bad row is stopped at the door, with a reason

Each good row becomes a typed ServiceVisit: a real date, a whole-number quantity. Each bad row becomes a Rejection with its line number, and is never saved.

So everything after this step can trust its input.

Read the four reasons out loud: missing serial, negative quantity, a 13th month, and the word "two". Line numbers match the CSV, so a technician can find and fix the row.

Type a row and see what the loader does with it

Serial and part numbers are trimmed and uppercased first. The part-number format comes from the manager's settings file, so a new format is a settings change, not a code change.

Try: change PATTERN to r"^P-\d{4,5}$" and the row is accepted. Or try a date of 2026-02-30, a quantity of 0, or an outcome of maybe.

"The clean visits now need a home that never loses a stock count, so Julian shows how they are stored."

Four tables, and one deliberate missing link

  • A visit that used two parts is one row in visits and two in parts_used.
  • Stock can go below zero. A negative count is how a shortfall stays visible.
  • parts_used doesn't point at stock, so a part missing from the stock list can still be saved and flagged later. That's what makes the 1.1.0 rollback safe.
Arrows are foreign keys, which SQLite only enforces because connect() turns them on for every connection. The red dashed line is the link we chose not to add.

One batch in, and the stock counts follow

save_visits groups rows by visit and saves each visit in one transaction: the equipment, the visit, its parts and the stock change.

P-1180 had 1 on hand. A visit used 3. The database says -2, and keeps saying it.

Point at the stock chart: the outline is the count from stock.csv, the solid bar is after the batch, the tick is the reorder level. Red is below zero, amber is at or under the reorder level.

A save that fails halfway leaves nothing behind

This visit's first part is fine. Its second breaks a rule in the schema. Because the whole visit is one transaction, the first part's write and its stock change are rolled back too.

Then we save a good visit twice: the second run is a duplicate and changes nothing.

The pairs of bars are identical: that's the point. Without the transaction, P-1001 would have dropped to 8 with no visit to explain it.

The rules read the whole history, not just today's file

Each rule asks the database one question and returns flags. The repeat-failure limits come from the manager's settings, so changing them is an edit to a file.

Try: COUNT = 2 or WINDOW = 120 and run again. More serials light up, with no code change.
Run with the defaults: only SW-4410 is shaded. SW-5120 has the most visits but they are months apart, which is what the rule is for. Then set COUNT = 2 live.

The container can go. The history stays.

FROM python:3.12.7-slim
WORKDIR /app
RUN pip install --no-cache-dir .
COPY data ./sample_data
USER app
ENV SERVICE_DB_PATH=/data/service.db
VOLUME ["/data"]
ENTRYPOINT ["service-tracker"]
  • Same Python and the same image on every laptop.
  • The database lives on the volume, so removing the container keeps every visit.
The Dockerfile is trimmed for the slide; the real one is in the repo. Emphasise "named volume": it's what the rollback relies on.

What the tests cover, and what they don't

Covered on every pull request

  • Each loader rejection reason and each settings error
  • Rollback of a half-saved visit, and reruns that save nothing twice
  • Each rule alone, a serial breaking two rules, a day with no flags
  • An integration test: the real CLI on the seed-42 files, checking the report and row counts
  • The Docker image builds

Not covered automatically

  • The volume surviving a removed container
  • Upgrade and rollback between the real images
  • Very large input files

Those are checked by the rollback drill, which we rehearse from a clean volume.

Being honest about gaps is the point of this slide. If asked "how would you test the rollback in CI?", the answer is a CI job that runs both image tags on one named volume.
